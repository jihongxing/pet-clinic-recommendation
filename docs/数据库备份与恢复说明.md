# 数据库备份与恢复说明

## 目标

这份文档对应 `T6-07`，用于把 staging 环境的 PostgreSQL 备份与恢复流程固定下来，确保明天真机联调或后续提审前，数据风险是可控的。

当前仓库已提供：

- PowerShell 备份脚本：`scripts/backup-staging-db.ps1`
- PowerShell 恢复脚本：`scripts/restore-staging-db.ps1`
- 本地备份目录约定：`backups/staging/`

## 1. 备份前提

1. staging 容器已经启动
2. 根目录已存在 `.env.staging`
3. 当前机器可执行 `docker compose`

如果你后面用的是 `podman compose`，把脚本参数里的 `ComposeBinary` 改成 `podman` 即可。

## 2. 手动执行一次备份

在仓库根目录运行：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\backup-staging-db.ps1
```

执行成功后会生成：

- `backups/staging/<DB_DATABASE>-yyyyMMdd-HHmmss.dump`
- `backups/staging/<DB_DATABASE>-latest.dump`

这些备份文件已被 `.gitignore` 忽略，不会误提交到仓库。

## 3. 建议的自动备份频率

建议至少：

- 每天凌晨 03:00 执行一次全量备份
- 每次正式提审前手动补一份
- 每次执行数据库结构变更前手动补一份

如果你用 Windows 服务器，可以把下面的命令放进“任务计划程序”：

```powershell
powershell -ExecutionPolicy Bypass -File D:\codeSpace\petMed\scripts\backup-staging-db.ps1
```

如果你用 Linux 服务器，建议把同等逻辑放进 `cron`。

## 4. 恢复数据库

恢复命令：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\restore-staging-db.ps1 -BackupFile .\backups\staging\pet_clinic_recommendation-latest.dump
```

注意：

- 该脚本会用 `pg_restore --clean --if-exists` 覆盖现有表结构和数据
- 恢复前一定先再做一份当前快照
- 恢复后建议立即验证 `/api/v1/health`

## 5. 恢复后最小验证

恢复完成后，至少检查：

1. `https://<DOMAIN_NAME>/api/v1/health`
2. 首页附近诊所列表是否正常返回
3. 诊所详情页是否能打开
4. `npm run seed:verify:tags`
5. `npm run seed:verify:clinics`

如果只是 staging 侧恢复，后两项也可以在后端容器内执行对应脚本完成校验。

## 6. 明天真机测试前建议

今晚如果你准备停工，建议最后做一次备份，明天真机测到脏数据或想回到干净状态时，直接执行恢复脚本即可。
