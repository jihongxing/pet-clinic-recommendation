# 上线回滚方案

## 目标

这份文档对应 `T6-11`，用于在 staging / 正式环境发生故障时，能在最短时间内把服务恢复到上一可用状态。

## 1. 哪些情况需要回滚

满足任一条件就不要硬扛，直接回滚：

- 健康检查持续失败：`/api/v1/health` 不通过
- 就绪探针持续失败：`/api/v1/health/ready` 不通过
- 首页列表或诊所详情主链路不可用
- 微信登录大面积失败
- 预约或评价接口持续 5xx
- Redis / PostgreSQL 连接异常且短时间无法修复

## 2. 回滚优先级

按下面顺序判断：

1. 先回滚应用版本
2. 再判断是否需要回滚数据库
3. 最后再处理域名 / Nginx / HTTPS 层问题

原则是尽量先恢复服务，再恢复理想状态。

## 3. 应用回滚步骤

### 3.1 回到上一个稳定提交

先在本地或服务器确认最近稳定版本的 commit：

```powershell
git log --oneline -n 10
```

### 3.2 在部署目录切到稳定提交

```powershell
git checkout <stable-commit>
```

### 3.3 重新拉起 staging

```powershell
docker compose --env-file .env.staging -f docker-compose.staging.yml up -d --build
```

### 3.4 验证

至少验证：

- `https://<DOMAIN_NAME>/api/v1/health/live`
- `https://<DOMAIN_NAME>/api/v1/health/ready`
- `https://<DOMAIN_NAME>/api/v1/health`
- 首页附近诊所接口
- 诊所详情接口
- 一次登录请求

## 4. 数据库回滚步骤

如果问题来自 migration、种子数据或写链路污染，再执行数据库回滚。

### 4.1 先备份当前坏状态

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\backup-staging-db.ps1
```

### 4.2 恢复到最近可用快照

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\restore-staging-db.ps1 -BackupFile .\backups\staging\pet_clinic_recommendation-latest.dump
```

### 4.3 再次验证主链路

- 微信登录
- 首页列表
- 诊所详情
- 创建预约
- 提交评价

## 5. Nginx / HTTPS 层回滚

如果是证书、域名或反向代理配置导致的问题：

1. 回退 `nginx/nginx.staging.conf.template`
2. 确认证书目录 `nginx/ssl/live/<DOMAIN_NAME>/` 是否完整
3. 重新执行：

```powershell
docker compose --env-file .env.staging -f docker-compose.staging.yml up -d nginx --force-recreate
```

4. 用 `curl` 验证：

```powershell
curl https://<DOMAIN_NAME>/api/v1/health/ready
curl https://<DOMAIN_NAME>/api/v1/health
```

## 6. 明天真机测试场景下的最小回滚

如果明天只是做小程序真机联调，最实用的回滚动作其实只有两件：

1. 回滚数据库到今天收工前的快照
2. 把前端 API 域名和后端部署都切回今天这版稳定代码

这样不用全量重做环境，恢复最快。

## 7. 回滚后复盘建议

回滚只是止血，后续建议补三件事：

1. 记录故障发生时间、表现和影响范围
2. 记录最终回滚到的 commit 和备份文件名
3. 把根因写进 `docs/CHANGELOG.md` 或单独复盘文档
