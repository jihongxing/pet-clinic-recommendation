# 实际落地实施计划

## 1. 当前项目现状

这个仓库目前处于“文档和原型先行，代码尚未落地”的阶段：

- `backend/` 只有 `package.json` 和 `.env.example`，没有 `src/`、`test/`、`Dockerfile`
- 仓库里没有真正的小程序前端目录，只有原型文件 `miniapp-prototype.html`
- `docker-compose.yml` 依赖 `backend/Dockerfile` 和 `nginx/nginx.conf`，但这两个文件当前不存在
- 数据库初始化脚本 `database/init.sql` 已经较完整，可作为后端数据层的第一版事实来源
- `docs/` 中 PRD、技术方案、API 文档、前端开发指南已经足够支持开始实现

结论：当前最缺的不是某一个功能，而是“可运行的应用骨架”。第一步必须先把后端、小程序、数据库、运行环境真正搭起来。

---

## 2. 现有设计资产拆解

### 2.1 数据库脚本已覆盖的核心域模型

`database/init.sql` 已经定义了以下核心对象：

- 用户：`user`
- 诊所：`clinic`
- 标签：`tag`
- 用户打标签明细：`user_tag_log`
- 诊所标签聚合：`clinic_tag_stat`
- 预约记录：`order`
- 标签生命周期日志：`tag_lifecycle_log`
- 推荐关系：`user_referral`
- 诊所标签回应：`clinic_tag_response`
- 异常行为记录：`abnormal_behavior`
- 就诊确认：`order_confirmation`
- 诊所详情视图：`v_clinic_detail`
- 地理函数：`calculate_distance`、`get_nearby_clinics`

这说明数据库已经不是“空白设计”，而是一个偏完整的 V1.0 数据底座。

### 2.2 原型页已覆盖的页面和交互

`miniapp-prototype.html` 当前包含以下页面流：

- 首页：附近诊所列表、距离筛选、标签筛选、口碑/性价比切换
- 搜索页
- 地图页
- 个人中心页
- 诊所详情页
- 标签评价页

评价页的真实交互是：

- 第一层：情绪选择
- 第二层：原因标签，按情绪切换标签池
- 第三层：补充标签
- 第四层：可选文字说明

注意：原型中的“第四层文字说明”比 PRD 更激进，实施前需要确认是否保留。

## 3. 现在必须补齐的设计缺口

这些问题不解决，代码实现过程中一定会反复返工。

### 3.1 打标签模型与“一人一诊所一次评价”规则不完全匹配

当前 `user_tag_log` 的唯一约束是 `(user_id, clinic_id, tag_id)`，它能防止同一标签重复提交，但不能真正防止“同一用户对同一诊所提交第二次评价”。

建议新增一层“评价主表”：

- `clinic_review`
- 字段建议：`id`、`user_id`、`clinic_id`、`order_id`、`emotion`、`source`、`review_text`、`submitted_at`
- 约束建议：`UNIQUE (user_id, clinic_id)`

然后 `user_tag_log` 作为评价子表，增加 `review_id` 外键。

### 3.2 评价页补充标签没有数据库映射

原型里的“猫更友好 / 狗更友好 / 急诊不错 / 有停车位 / 交通方便 / 可以洗澡”没有出现在 `tag` 初始化数据中。

建议二选一：

- 方案 A：把这些作为 L1/L2/L4 中的低权重标签入库
- 方案 B：单独建 `review_extra_tag` 配置表，不参与主排序

推荐方案 B，因为这批标签偏辅助信息，不应污染核心排序。

### 3.3 情绪枚举不一致

原型页使用的是 `satisfied / normal / unsatisfied`，数据库和 API 文档使用的是 `satisfied / neutral / unsatisfied`。

必须统一成一套，推荐统一为：

- `satisfied`
- `neutral`
- `unsatisfied`

### 3.4 预约状态与 API 文档不一致

API 文档里“确认未就诊”会返回 `cancelled`，但 `order_status` 只有：

- `clicked`
- `confirmed`

建议将 `order_status` 扩展为：

- `clicked`
- `confirmed`
- `cancelled`

### 3.5 诊所认领和回应能力缺少账户体系

数据库有：

- `clinic.is_claimed`
- `clinic_tag_response`

但没有：

- 诊所后台账户
- 认领申请记录
- 审核角色

如果要做“诊所回应”上线版，至少需要补：

- `clinic_account`
- `clinic_claim_request`
- `admin_user` 或统一后台用户角色表

### 3.6 提醒与消息发送缺少任务记录

文档要求：

- 用户预约后 24 小时提醒确认是否就诊

当前数据库没有消息任务表。建议新增：

- `message_task`
- `message_delivery_log`

如果第一版不接微信模板消息，可以先做站内待办，但数据结构仍建议先预留。

## 4. 推荐实施策略

不要按文档里“所有能力同时落地”的方式开工。正确顺序应该是：

1. 先搭可运行骨架
2. 先打通读路径
3. 再打通写路径
4. 再落排序与风控
5. 再补增强功能
6. 最后做部署和上线验证

推荐拆成两个目标：

### 4.1 M1：可上线 MVP

范围建议：

- 微信登录
- 首页附近诊所列表
- 诊所详情
- 标签列表
- 轻预约点击
- 评价提交流程
- 基础标签聚合与分数计算
- 搜索
- 基础日志、错误监控、Swagger

### 4.2 M1.5：增强版

范围建议：

- 就诊确认
- 诊所回应
- 风险标签自动触发
- 社交传播标签推断
- 数据分析漏斗
- Prometheus + Grafana + 告警

这样做的原因是：当前仓库没有任何业务代码，如果把全部增强能力作为第一目标，落地周期会明显拖长。

## 5. 从脚手架到落地的完整实施计划

以下按“一个 1-2 人小团队，4-6 周完成第一版上线”来设计。

### Phase 0：项目校准与仓库补骨架（第 1-2 天）

目标：让仓库从“文档项目”变成“可开发项目”

任务清单：

- 创建 NestJS 后端工程目录结构
- 建立 `src/modules`、`src/common`、`src/config`、`src/database`、`src/tasks`
- 补齐 `backend/tsconfig.json`、`nest-cli.json`、`eslint`、`prettier`
- 新建 `backend/Dockerfile`
- 新建 `nginx/nginx.conf`
- 初始化微信小程序目录 `frontend/`
- 创建 `app.js`、`app.json`、`app.wxss`
- 在 README 中改写“当前实际可运行方式”
- 约定分支策略、环境变量模板、提交规范

输出物：

- 本地可以 `docker compose up`
- 后端容器可启动
- 小程序工程可以在开发者工具中打开

### Phase 1：数据库与后端基础设施（第 3-5 天）

目标：建立可持续开发的后端底座

任务清单：

- 决定 ORM 方式：TypeORM 实体优先，SQL 脚本保留为初始化参考
- 将 `init.sql` 拆成 TypeORM migrations
- 建立数据库连接、Redis 连接、ConfigModule
- 建立全局异常过滤器、响应拦截器、校验管道
- 接入 Swagger
- 接入 JWT 鉴权
- 建立基础日志系统（Winston）
- 建立健康检查接口 `/health`

实现顺序建议：

- 先跑通 PostgreSQL + Redis
- 再完成 migration 执行
- 再搭鉴权和基础模块

输出物：

- 后端应用可启动
- 数据库可迁移
- Swagger 可访问
- 基础健康检查通过

### Phase 2：核心读路径（第 6-10 天）

目标：先让用户“能看”

后端任务：

- 实现 `POST /auth/login`
- 实现 `GET /tags`
- 实现 `GET /clinics/nearby`
- 实现 `GET /clinics/:id`
- 实现搜索接口 `GET /clinics/search`
- 补齐 DTO、Entity、Repository、Service、Controller
- 实现 Redis 缓存策略

数据库补充：

- 为搜索增加索引，推荐先用 `pg_trgm`
- 确认 `clinic.location` 写入和查询方式
- 准备北京首批 50-100 家种子诊所数据

前端任务：

- 搭首页
- 搭搜索页
- 搭地图页
- 搭详情页
- 封装请求层和登录态
- 处理定位授权、失败兜底、空态与加载态

输出物：

- 用户能打开小程序
- 能看到附近诊所
- 能切换口碑/性价比
- 能看详情与地图

### Phase 3：核心写路径（第 11-15 天）

目标：让关键闭环“预约 -> 评价”真的跑起来

后端任务：

- 增加 `clinic_review` 主表和迁移
- 调整 `user_tag_log` 结构，增加 `review_id`
- 实现 `POST /orders`
- 实现 `GET /orders/my`
- 实现 `POST /tags/submit`
- 实现 `GET /tags/selection-config`
- 保证“一人一诊所只能评价一次”
- 实现提交幂等与限流

前端任务：

- 详情页接入“打电话 / 复制微信 / 去评价”
- 评价页三层标签流转
- 可选文字说明是否保留，实施前定版
- 我的预约页
- 我的评价页

关键决策：

- 原型里的第四层文字说明默认建议先保留，但不参与排序
- 文字说明只做展示留存，不做公开长评论流

输出物：

- 用户可以点击预约
- 用户可以完成评价
- 数据能真正写入数据库

### Phase 4：聚合统计与评分引擎（第 16-20 天）

目标：让列表排序从“静态字段”变成“真实算法结果”

任务清单：

- 实现标签提交流程后的统计更新
- 实现 `clinic_tag_stat` 聚合逻辑
- 实现标签生命周期状态机
- 实现 ScoreCalculator
- 实现 `reputation_score`、`price_score`、`confidence_factor` 预计算
- 增加 cron 任务
- 补齐缓存失效策略

建议先做的算法范围：

- L1 正向标签生效
- 基础 RiskPenalty
- 小样本保护
- 用户去重
- 时间衰减

建议后放的范围：

- L4 社交传播自动推断
- 复杂异常模式分析

输出物：

- 首页排序与标签统计真实联动
- 新评价会影响列表结果

### Phase 5：风控、验证、回应、可观测性（第 21-26 天）

目标：把系统从“能用”提升为“敢上线”

风控任务：

- Redis 限流
- 新用户权重
- 设备/IP 异常检测
- 异常行为落库

业务增强任务：

- 实现 `POST /orders/:id/confirm-visit`
- 实现就诊确认状态流转
- 实现 `POST /clinics/:id/responses`
- 实现 `GET /clinics/:id/responses`

基础设施任务：

- Prometheus 指标 `/metrics`
- Grafana 仪表盘
- 告警规则
- 请求日志、慢查询日志、任务日志

说明：

- 如果上线窗口紧，可以把“诊所回应”放到 M1.5
- 但日志、错误监控、限流最好不要省

输出物：

- 可以监控系统健康
- 可以发现异常行为
- 关键闭环完整

### Phase 6：联调、测试、部署、提审（第 27-30 天）

目标：完成真正的上线准备

测试任务：

- 单元测试：核心服务、评分引擎、标签提交流程
- 集成测试：登录、列表、详情、下单、评价
- E2E 测试：至少覆盖主链路
- 小程序真机测试
- 性能压测：列表、详情、标签提交

部署任务：

- 完善 `docker-compose.yml`
- 准备 staging 环境
- 配置域名、HTTPS、微信合法域名
- 配置数据库备份
- 配置 PM2 或容器编排

发布任务：

- 准备测试账号
- 准备小程序提审素材
- 准备灰度数据
- 准备上线回滚方案

输出物：

- staging 可验收
- production 可部署
- 小程序可提审

## 10. 建议的下一步执行顺序

最推荐的开工顺序如下：

1. 先补后端和前端脚手架
2. 先把 `init.sql` 转成 migrations
3. 先实现登录、标签、诊所列表、诊所详情
4. 再实现预约和评价闭环
5. 再做分数聚合和排序
6. 最后补风控、监控、部署

## 11. 如果按我来推进，建议第一周就做这些

第一周目标不是“做完很多功能”，而是建立真正可迭代的开发基线：

- Day 1：后端 NestJS 工程初始化 + Dockerfile + PostgreSQL/Redis 启动
- Day 2：前端小程序工程初始化 + 全局样式 + 登录态封装
- Day 3：数据库 migrations 落地 + 标签/诊所实体建模
- Day 4：完成 `/auth/login`、`/tags`、`/clinics/nearby`
- Day 5：完成 `/clinics/:id`，首页和详情页联调

第一周结束的验收标准：

- 本地一键启动成功
- 小程序能登录
- 首页能看到附近诊所
- 点卡片能看详情

---

## 12. 最关键的实施原则

- 先打通主链路，再做增强功能
- 先保证数据结构能支撑规则，再写页面
- 先做可运行骨架，再谈算法优化
- 先把排序简版跑起来，再逐步引入 L3/L4
- 先上线可信 MVP，再扩展成完整信用系统

一句话总结：

这个项目完全可以落地，但当前第一优先级不是“继续补文档”，而是立刻进入“脚手架搭建 -> 核心链路实现 -> 排序引擎落地 -> 上线准备”的执行阶段。
