# 生产日志与监控说明

## 目标

`T6-08` 的目标不是“把容器跑起来”，而是上线后出了问题，能在几分钟内定位：

- 是后端报错
- 还是 Nginx 反向代理层异常
- 是错误率升高
- 还是响应时间退化

当前仓库已经把这条链路接通：

- `backend` 产出结构化 JSON 日志
- `nginx` 产出结构化 access log 和 error log
- `promtail` 采集日志
- `loki` 存储日志
- `prometheus` 采集 `/metrics`
- `grafana` 统一展示日志和指标

## 组件说明

### 日志

- Backend 日志目录：容器内 `/app/logs`
- Nginx 日志目录：容器内 `/var/log/nginx`
- 采集器：`promtail`
- 存储：`loki`

Backend 的请求日志和错误日志里已经带有这些关键字段：

- `requestId`
- `path`
- `statusCode`
- `durationMs`
- `userId`

这意味着排查某个 500 请求时，可以从 Grafana 日志面板直接按 `requestId` 或 `path` 过滤。

### 指标

Prometheus 当前重点采集：

- `api_requests_total`
- `api_request_errors_total`
- `api_response_time_seconds`
- 默认进程指标，例如内存和事件循环相关指标

Grafana 当前重点展示：

- QPS
- 错误率
- P95 响应时间
- 各接口请求量
- 各接口 5xx 错误率
- backend / nginx 日志流

## 部署后检查清单

1. 容器状态

```powershell
docker compose --env-file .env.staging -f docker-compose.staging.yml ps
```

2. 后端就绪探针

```powershell
curl https://<DOMAIN_NAME>/api/v1/health/ready
```

3. 后端存活探针

```powershell
curl https://<DOMAIN_NAME>/api/v1/health/live
```

4. Loki 就绪

```powershell
curl http://localhost:3100/ready
```

5. Backend 指标端点

```powershell
curl http://localhost:3000/metrics
```

4. Grafana 数据源

进入 Grafana 后，应该能看到两个已预置数据源：

- `Prometheus`
- `Loki`

## 推荐排障路径

### 1. API 变慢

先看 Grafana:

- `PetMed Backend Overview`
- `P95 Response Time`
- `Response Time by Endpoint`

如果某个接口明显升高，再切到 `PetMed Production Observability` 看对应 `path` 的 backend 日志。

同时确认：

- `/api/v1/health/ready` 是否返回 `200`
- `/api/v1/health/live` 是否持续正常

### 2. 5xx 升高

先看：

- `API Error Rate`
- `5xx Error Rate by Endpoint`

再查日志：

- `Backend Error Logs (5m)`
- `Backend Logs`

如果后端没有明显异常，再看 `Nginx Error Logs (5m)` 和 `Nginx Logs`。

### 3. 用户反馈“偶发失败”

优先让客户端带上 `x-request-id`，或者直接记录接口响应头中的 `x-request-id`。

后端和 Nginx 日志链路里都能围绕这个 ID 继续追。
