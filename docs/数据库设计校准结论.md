# 数据库设计校准结论

> 目标：解决当前 `database/init.sql`、PRD、API 文档、原型页之间的关键设计不一致问题  
> 用途：作为后续 TypeORM Entity 与 migration 的唯一落地依据

---

## 1. 校准范围

本次只处理会直接影响开发和 migration 的结构性问题，不在这里展开算法实现细节。

重点校准对象：

- 用户评价主模型
- 情绪枚举
- 补充标签存储方案
- 预约状态模型
- 诊所认领/回应最小数据结构
- 预约后提醒任务的最小数据结构

---

## 2. 当前发现的关键不一致

### 2.1 “一人一诊所一次评价”规则与当前表结构不完全匹配

当前 `user_tag_log` 的唯一约束是：

```sql
UNIQUE (user_id, clinic_id, tag_id)
```

这只能防止：

- 同一用户对同一诊所重复提交同一个标签

但不能真正防止：

- 同一用户对同一诊所再次发起一次新的评价，只是换了一组标签

而 PRD 明确要求：

- 同一用户同一诊所只能一次评价

结论：

- 必须引入“评价主表”

### 2.2 原型页和数据库情绪枚举不一致

当前数据库与 API 文档使用：

- `satisfied`
- `neutral`
- `unsatisfied`

原型页使用：

- `satisfied`
- `normal`
- `unsatisfied`

结论：

- 全部统一为 `neutral`

### 2.3 原型页第三层补充标签没有数据库承载

原型存在以下补充标签：

- 猫更友好
- 狗更友好
- 急诊不错
- 有停车位
- 交通方便
- 可以洗澡

但当前 `tag` 初始化数据中没有这批标签。

结论：

- 这批标签不进入核心 `tag` 表，不参与主排序
- 应单独建“补充标签配置表”和“补充标签选择表”

### 2.4 预约状态与 API 文档不一致

当前 `order_status` 只有：

- `clicked`
- `confirmed`

但 API 文档中确认未就诊时返回：

- `cancelled`

结论：

- `order_status` 必须新增 `cancelled`

### 2.5 诊所认领/回应缺少身份主体

当前库里有：

- `clinic.is_claimed`
- `clinic.expire_at`
- `clinic_tag_response`

但没有：

- 诊所登录账户
- 认领申请记录
- 谁审核了认领

结论：

- 至少补齐最小的认领账户模型

### 2.6 预约后 24 小时提醒没有任务承载

PRD 和 API 都要求“预约后确认是否就诊”，但当前数据库没有消息任务表。

结论：

- 需要至少有一张消息任务表，用于延迟提醒和状态追踪

---

## 3. 最终定稿：评价模型

### 3.1 新增评价主表 `clinic_review`

这是本次校准最重要的新增表。

建议结构：

```sql
CREATE TYPE review_source AS ENUM ('order', 'normal');
CREATE TYPE review_status AS ENUM ('submitted', 'hidden');

CREATE TABLE clinic_review (
  id BIGSERIAL PRIMARY KEY,
  user_id BIGINT NOT NULL,
  clinic_id INTEGER NOT NULL,
  order_id BIGINT,
  emotion emotion_type NOT NULL,
  source review_source NOT NULL DEFAULT 'normal',
  review_text VARCHAR(500),
  submitted_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  status review_status NOT NULL DEFAULT 'submitted',

  CONSTRAINT uk_clinic_review_user_clinic UNIQUE (user_id, clinic_id)
);
```

说明：

- `UNIQUE (user_id, clinic_id)` 才能真正实现“一人一诊所一次评价”
- `order_id` 可为空，用来区分预约后评价和普通评价
- `review_text` 用于承载原型页第四层可选文字说明
- `status` 先保留最小能力，支持后续隐藏违规评价

### 3.2 调整 `user_tag_log`

`user_tag_log` 不再是“评价主表”，而是“评价标签明细表”。

建议新增字段：

```sql
review_id BIGINT NOT NULL
```

建议新增外键：

```sql
FOREIGN KEY (review_id) REFERENCES clinic_review(id) ON DELETE CASCADE
```

建议调整唯一约束为：

```sql
UNIQUE (review_id, tag_id)
```

说明：

- 一个评价内不能重复选择同一标签
- 真正的“一次评价”规则由 `clinic_review` 保证
- `user_id` 和 `clinic_id` 可以在 `user_tag_log` 保留，方便查询和聚合

### 3.3 是否保留 `emotion` 在 `user_tag_log`

结论：

- 保留也可以，但不建议作为主来源
- `emotion` 以 `clinic_review.emotion` 为准

推荐做法：

- `clinic_review` 保存主情绪
- `user_tag_log` 不再保存 `emotion`

理由：

- 避免一份事实被重复存两次，后续出现数据不一致

## 4. 最终定稿：情绪枚举

统一使用：

```sql
CREATE TYPE emotion_type AS ENUM ('satisfied', 'neutral', 'unsatisfied');
```

系统内所有相关层统一为：

- 数据库
- API DTO
- 前端页面状态
- 标签选择配置接口

原型页里的 `normal` 必须在代码实现时改为 `neutral`。

---

## 5. 最终定稿：补充标签模型

### 5.1 设计原则

补充标签：

- 不参与核心排序
- 不进入 L1-L4 主标签体系
- 仅作为详情展示和用户参考信息

### 5.2 新增补充标签配置表 `extra_tag_option`

```sql
CREATE TABLE extra_tag_option (
  id SERIAL PRIMARY KEY,
  name VARCHAR(50) NOT NULL,
  weight NUMERIC(3, 2) DEFAULT 0.3,
  sort_order INTEGER DEFAULT 0,
  status SMALLINT DEFAULT 1,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

  CONSTRAINT uk_extra_tag_option_name UNIQUE (name)
);
```

初始化数据：

- 猫更友好
- 狗更友好
- 急诊不错
- 有停车位
- 交通方便
- 可以洗澡

### 5.3 新增补充标签选择表 `review_extra_tag_log`

```sql
CREATE TABLE review_extra_tag_log (
  review_id BIGINT NOT NULL,
  extra_tag_option_id INTEGER NOT NULL,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

  PRIMARY KEY (review_id, extra_tag_option_id)
);
```

说明：

- 一个评价最多选择 2 个补充标签，这条限制放在应用层校验
- 这批数据默认不进入 `clinic_tag_stat`
- 如果未来想对“猫友好”做筛选，再单独扩展聚合表

## 6. 最终定稿：预约状态模型

### 6.1 扩展 `order_status`

原有：

```sql
('clicked', 'confirmed')
```

调整为：

```sql
('clicked', 'confirmed', 'cancelled')
```

### 6.2 状态含义

- `clicked`：用户点击电话/微信，已记录轻预约行为
- `confirmed`：用户确认已就诊
- `cancelled`：用户明确反馈未就诊或放弃

### 6.3 `order_confirmation` 是否保留

结论：

- 保留

理由：

- `order.status` 记录当前结果
- `order_confirmation` 记录确认动作本身，便于审计和分析

---

## 7. 最终定稿：诊所认领与回应最小模型

当前 `clinic_tag_response` 不能独立工作，因为没有诊所身份体系。

### 7.1 新增 `clinic_account`

```sql
CREATE TABLE clinic_account (
  id BIGSERIAL PRIMARY KEY,
  clinic_id INTEGER NOT NULL,
  username VARCHAR(100) NOT NULL,
  password_hash VARCHAR(255) NOT NULL,
  status SMALLINT DEFAULT 1,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

  CONSTRAINT uk_clinic_account_username UNIQUE (username),
  CONSTRAINT uk_clinic_account_clinic UNIQUE (clinic_id)
);
```

说明：

- 一个诊所先只允许一个后台账户
- 后续如需多账号再扩展

### 7.2 新增 `clinic_claim_request`

```sql
CREATE TYPE claim_status AS ENUM ('pending', 'approved', 'rejected');

CREATE TABLE clinic_claim_request (
  id BIGSERIAL PRIMARY KEY,
  clinic_id INTEGER NOT NULL,
  applicant_name VARCHAR(100) NOT NULL,
  applicant_phone VARCHAR(30) NOT NULL,
  proof_material TEXT,
  status claim_status NOT NULL DEFAULT 'pending',
  reviewed_by BIGINT,
  reviewed_at TIMESTAMP,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

说明：

- 这张表是认领流程的最小可审计单据
- `reviewed_by` 先不强绑后台用户体系，后续有 `admin_user` 再补外键

### 7.3 `clinic_tag_response` 的使用前提

最终约束：

- 只有 `clinic.is_claimed = 1`
- 且存在有效 `clinic_account`
- 才允许提交回应

---

## 8. 最终定稿：提醒任务模型

### 8.1 新增消息任务表 `message_task`

```sql
CREATE TYPE message_task_type AS ENUM ('order_followup');
CREATE TYPE message_task_status AS ENUM ('pending', 'sent', 'failed', 'cancelled');

CREATE TABLE message_task (
  id BIGSERIAL PRIMARY KEY,
  user_id BIGINT NOT NULL,
  clinic_id INTEGER NOT NULL,
  order_id BIGINT NOT NULL,
  task_type message_task_type NOT NULL,
  planned_at TIMESTAMP NOT NULL,
  sent_at TIMESTAMP,
  status message_task_status NOT NULL DEFAULT 'pending',
  payload JSONB,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

说明：

- 第一版至少支持“预约后 24 小时确认是否就诊”
- 即便暂时不接微信模板消息，也可以先作为系统任务和补偿机制的基础

## 9. 对现有表的最终调整清单

### 9.1 `user_tag_log`

变更：

- 新增 `review_id`
- 删除 `emotion`
- 唯一约束改为 `(review_id, tag_id)`

### 9.2 `order`

变更：

- `order_status` 增加 `cancelled`

### 9.3 `clinic`

结论：

- `is_claimed` 和 `expire_at` 保留
- 不额外改动

### 9.4 `tag`

结论：

- 主标签体系不吸收原型第三层补充标签
- 继续只承载 L1-L4 核心标签

---

## 10. migration 实施顺序

后续做 `T1-01` 时，建议按下面顺序拆 migration：

1. 建基础枚举和基础表
2. 建 `clinic_review`
3. 调整 `user_tag_log`
4. 扩展 `order_status`
5. 建 `extra_tag_option` 和 `review_extra_tag_log`
6. 建 `clinic_account` 和 `clinic_claim_request`
7. 建 `message_task`
8. 初始化种子数据

---

## 11. 本次校准的最终结论

这一版数据库落地时必须遵守以下结论：

- 用 `clinic_review` 承担“一次评价”的主事实
- 用 `user_tag_log` 承担“评价标签明细”
- 情绪枚举统一为 `satisfied / neutral / unsatisfied`
- 原型第三层补充标签走独立表，不污染主标签体系
- `order_status` 增加 `cancelled`
- 诊所回应能力必须配最小认领账户结构
- 预约后提醒必须有任务表承载

一句话总结：

后续 migration 不应直接照搬当前 `init.sql`，而应以这份校准结论为准做结构升级。
